# Validation — Phase 9: Advanced capabilities (Web Share)

Implementation is done and mergeable when every item below is checked, with concrete evidence (screenshot, console output, or explicit test description) — not just "looks right".

## Location-from-URL parsing

- [x] `locationFromSearchParams` returns a correct location object for valid `lat`/`lng`/`tz`/`label` params, verified directly (standalone Node script, no build step).
- [x] Missing/invalid `tz` falls back to the device timezone, not left undefined or throwing — verified for both a missing `tz` param and an invalid one (`Not/AZone`).
- [x] Missing `label` falls back to `'Shared location'`.
- [x] Missing or out-of-range `lat`/`lng` returns `null` — verified for missing `lat`, missing `lng`, out-of-range (`lat=200`), and non-numeric (`lat=abc`).
- [x] A shared location takes priority over any existing cached location on load, is itself cached afterwards, and the query string is stripped from the visible URL post-load — verified end-to-end via CDP (`?lat=48.8566&lng=2.3522&tz=Europe%2FParis&label=Paris%2C%20France` → label "Paris, France", `location.search` empty after load, `localStorage`'s cached location shows the Paris coordinates with `source: "shared-link"`). A subsequent plain reload of the same tab kept showing Paris (from cache), confirming persistence.
- [x] A malformed query string (`lat=not-a-number`) falls back cleanly to the normal cached/default location (rendered "London, England, UK") — no crash, no console error.
- [x] Location card (`#location-details`) stays collapsed on a shared-link load (`locationDetailsOpen: false`), same as an existing-cached-location load.
- [x] **Critical bug found and fixed during this pass:** the original implementation used `Number(params.get('lat'))` without first checking the param was present. `Number(null)` evaluates to `0`, not `NaN` — so a page load with *no query string at all* (the overwhelming normal case) was silently parsed as a "valid" `{lat: 0, lng: 0}` shared location and would have overridden the cached/default location on every single visit. Fixed by adding explicit `params.has('lat')`/`params.has('lng')` checks before parsing. Re-verified: an empty query string now correctly returns `null`, while an explicitly-present `lat=0&lng=0` (a legitimate location, e.g. near the equator/prime meridian) still correctly parses as valid.
